# astro-blog

## Purpose
This is the Astro 6 static-site publishing target for BlogBlaster. It ingests Markdown and MDX blog post files from `src/content/blog/`, validates their front matter via Astro content collections, and builds a fully static site deployable to Cloudflare Pages, Netlify, Vercel, or GitHub Pages. It is intentionally a standalone package — separate from the BlogBlaster backend — and receives generated content either by direct file drop or via the PowerShell sync script.

## For AI Agents

### Working In This Directory
- Posts must live at `src/content/blog/*.md` or `src/content/blog/*.mdx`; Astro's content collection system picks them up automatically.
- Required front matter fields: `title`, `description`, `pubDate`. Optional: `updatedDate`, `draft` (default `false`), `tags` (array), `canonicalUrl` (URL string), `heroImage` (string). See `src/content.config.ts` for the full Zod schema.
- `PUBLIC_SITE_URL` must be set at build time for the sitemap and canonical URLs to resolve correctly.
- Do not modify `dist/` — it is generated by `npm run build` and not tracked in git.
- This package has no TypeScript path aliases beyond `baseUrl: "."`.
- This subtree is a cloned deployable blog template used when provisioning customer blogs for the SaaS. It is tracked in git and can be developed here, but it is excluded from the default core BlogBlaster jCodeMunch index. Index it separately only for template-specific work.
- `.github/workflows/deploy-cloudflare.yml` builds and deploys `dist/` to Cloudflare Pages via `cloudflare/wrangler-action@v3` (direct upload) on every push to `main`. Requires GitHub secrets `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` and variable `CLOUDFLARE_PROJECT_NAME`; the deploy step is skipped (with a `::notice::`) when either secret is unset, so cloned templates don't fail CI before Cloudflare is configured.
- There are two mutually exclusive Cloudflare Pages deployment mechanisms — see the README's "Cloudflare Pages deployment" section for the full comparison: (A) a git-connected Pages project (recommended; Cloudflare builds on push, deployments carry a `commit_hash` the backend can match exactly) vs (B) this CI workflow's direct upload (deployments carry no `commit_hash`, so backend verification falls back to a `created_on`-after-push time-window match). Enable only one per site.
- This workflow is the client-side half of Cloudflare Pages deployment; the backend half (deploy hook trigger + deployment-status polling) lives in `backend/services/pipeline/publishing_cloudflare.py` and is driven by each site's `deploy_provider`/`cloudflare_project_name`/`cloudflare_deploy_hook_env_var` config fields.

### Testing Requirements
- `npm run dev` — starts Astro dev server (hot-reload, content collection watching)
- `npm run build` — full static build; confirms content schema validation and page generation
- `npm run check` — TypeScript/Astro type-check without building
- There are no automated test files; correctness is verified by a clean build.

### Common Patterns
- Config reads `process.env.PUBLIC_SITE_URL` at config-load time, not at runtime.
- All Astro pages filter out `draft: true` posts before rendering.
- Posts are always sorted descending by `pubDate`.
- MDX and Markdown are both supported — the `mdx()` integration is registered first.
